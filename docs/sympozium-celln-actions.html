SHIPPING · HERMETIC ACTIONS FIRST

Celln is Sympozium's execution choice for hermetic actions — not an Ensemble runtime.

Sympozium owns normal agents, AgentRuns, pipelines, delegation, shared memory, retries, and NATS/IPC — none of that moves. Celln is selected, per run, when a task is one bounded, risky, or sensitive computation that should execute in a sealed cell and return an immutable receipt, instead of a Kubernetes Job.

What's real today: set spec.backend: celln on an AgentRun and Sympozium's controller dispatches it to a Celln router instead of creating a Job (agentrun_celln.go) — no separate CRD, no proposed API, an existing field on the resource you already use. It builds a forge-mode celln.dev/v1alpha1 ExecutionRequest from the run's task and submits it to POST /v1/executions directly — the same hash-pinned contract the dispatcher proves out. Verified end-to-end on real hardware: real receipt back, real result on the AgentRun.

Execution choice in the Sympozium UX

EXISTING

Standard AgentRun

Use for normal assistants, workflows, Ensembles, delegation, model credentials, shared memory, IPC, NATS, skills, and streaming results.

Backend: Kubernetes Job or Agent Sandbox.

PREFERRED FOR RISKY WORK

Celln hermetic action

Use for one immutable tool/program, declared inputs, named egress, bounded output, timeout, and hardware isolation.

Result: immutable output artifact plus Celln execution receipt.

NOT SUPPORTED

Celln Ensemble / AgentRun

Do not select Celln for an AgentRun that needs agent-runner, ipc-bridge, shared /ipc, NATS delegation, workflow memory, or token/result lifecycle.

Behavior: reject explicitly; never downgrade.

Control-plane ownership

The actual API — an existing field, not a new CRD

apiVersion: sympozium.ai/v1alpha1
kind: AgentRun
spec:
  agentRef: my-agent
  task: "Parse this untrusted file and summarize its structure"
  backend: celln          # instead of a Kubernetes Job
  timeout: "5m"
status:
  phase: Pending | Running | Succeeded | Failed
  cellnActionId: string    # the id this run was dispatched to Celln with
Enforced today, in the controller, not just documented: backend: celln together with agentSandbox.enabled: true is rejected explicitly at admission — one execution backend, chosen unambiguously, never a silent fallback. A wedged Celln backend that never returns a terminal phase fails the run on a controller-side deadline rather than leaving it Running forever. Policy validation and token-budget checks run before Celln dispatch, same as the Job path.

Which lane does an AgentRun run in?

Always the agent lane, never the tool lane — and it's worth knowing why, not just that. The controller builds every dispatch as a forge request (Forge: &executionForge{Task: task} in agentrun_celln.go): the AgentRun's task string goes to a model, which writes a program, which gets rebuilt twice and hash-compared. That program is author=agent by construction, permanently, regardless of how cleanly it reproduces — and agent-authored code is agent-lane authority, full stop, the same rule the agent lane page covers for celln agent at the CLI. There is no path in today's AgentRun API to hand Celln a pre-declared, hash-pinned tool spec instead — that's the celln spec/celln run workflow on the tool lane page, and it isn't exposed through Sympozium yet.

What that means practically for a backend: celln run, taken straight from the request Sympozium actually sends:

  • Only the generated program executes — no ambient host tools, no filesystem outside its own workspace, no network unless a future revision adds egress declarations to the request (none does today).
  • workspace: "none" — nothing persists between runs; there's no volume to mount a prior run's output into.
  • Memory and output are fixed, not per-run configurable yet: 256MiB and a 64KiB output cap (cellnMemoryBytes/cellnOutputBytes in the controller). A task whose generated program needs more of either doesn't have a way to ask.
  • requireHardwareIsolation: true always — no fallback to a softer boundary if no KVM node is available; the run fails at dispatch instead.

If a task genuinely needs tool-lane authority — running an already-attested binary rather than agent-generated code — that's a reason to use the celln CLI directly against a spec file, not backend: celln on an AgentRun. Whether that gap gets closed (an AgentRun field naming a pre-declared tool spec instead of a task string) is open; nothing here proposes it yet.

What's implemented, and what's next

  1. Done. The Celln dispatcher resolves content hashes, creates a Warden/microVM/sealed cell, executes the declared program, dissolves it, and returns a validated receipt — proven end to end on real KVM hardware, through the actual deployed Kubernetes router.
  2. Done. Sympozium's controller dispatches backend: celln runs directly — no separate controller, no overloaded Job name, real status/phase mapping and a real deadline backstop.
  3. Done. The controller speaks the hash-pinned celln.dev/v1alpha1 contract, not a free-form task submission — the run's task becomes a forge request, the AgentRun's own model: field still doesn't apply (Celln uses whatever provider is configured on the host, unchanged), and the receipt's bounded output lands directly on AgentRun.status.result.
  4. By design, not a gap. Celln does not participate in delegation or shared memory. A parent AgentRun that needs those stays on the Job/Agent Sandbox backend; nothing here proposes changing that.
