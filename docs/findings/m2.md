# Findings — M2 (sealing half): claim C1 survives

Date: 2026-08-01 · Host: x86_64, kernel 7.1.3, Intel VT-x, `/dev/kvm`
Raw numbers: `bench/results/m1-m2-kvm.json` (`make bench-kvm` regenerates)
Tests: `make test-kvm` · Demo: `make demo-kvm`

> **C1 — "A guest, even at ring 0, cannot modify lent tool code; one physical
> copy serves N guests."** Both halves now hold on real hardware. The build plan
> called this the milestone most likely to kill or bless the project. It blesses
> it, with one important caveat (the VFS join, below) still outstanding.

## What was proven

### 1. Sealing holds against a guest that controls its own address translation

The weak version of this test — "a privileged guest write bounces" — was already
green in M1. The version that matters is the one where the guest is not merely
privileged but **owns the translation layer**:

`ring0_guest_with_own_page_tables_cannot_write_sealed_pages` builds a guest that
enters 32-bit protected mode, installs a page directory and page table **it wrote
itself**, identity-maps the first 4 MiB with the writable bit set — including the
sealed tool page — and then writes to it.

Guest-side, that write is entirely legal: CPL 0, PTE present + writable, no page
fault. It still does not land. The CPU takes an EPT violation and exits to the
host (`KVM_EXIT_MMIO`); the tool bytes are unchanged. The test asserts all three
facts — the guest's own PTE says writable, the write was refused, the bytes are
intact — plus a completion marker proving the guest reached the end of its 32-bit
code rather than dying early.

This is the difference between *"the guest kernel enforces it"* and *"the
hardware enforces it against the guest kernel"*, and it is the whole basis for
lending tool code to an untrusted agent.

### 2. One physical copy serves N cells

Tool page-sets are keyed by content hash in a process-global registry: N cells
loaning the same hash map **one** host allocation, read-only. Measured with a
1 MiB tool across 500 cells, all of which executed out of it:

| | |
|---|---|
| distinct host page-sets | **1** |
| naive cost (500 private copies) | 512,000 KiB |
| actual host RSS growth | **7,236 KiB** |
| saving | **71×** |

The residual growth is per-cell VM overhead (~12 KiB/cell), not tool
duplication.

### 3. Revocation reaches already-running cells

Deleting the memslot revokes pages from a live guest. Across 200 running cells
holding the tool: **9.8 ms wall (49 µs/cell)**, gate was < 1 s. All 200 read the
tool before revocation and unmapped zeros after.

### 4. Memslot budget — measured, not assumed

The build plan flagged KVM memslot limits as a possible forcing function for
coarser layer packing (ADR-0004). Measured on this host: **32,762 sealed
memslots in a single VM** before `KVM_SET_USER_MEMORY_REGION` refuses.

**Consequence: per-tool sealing is viable.** A cell would need >32k
independently-sealed tools to hit the ceiling, far beyond any plausible working
set. Layer packing remains useful for other reasons (fewer, larger mappings;
manifest deltas) but it is **not forced by the memslot budget**.

### 5. M1 gates, at scale

| Metric | Measured | Gate |
|---|---|---|
| cells forked, all reaching guest instructions | **1000 / 1000** | ≥ 1000 |
| fork p50 / p99 / max | 204 µs / **500 µs** / 3.2 ms | p99 < 5 ms |
| first guest instruction, p99 | 141 µs | — |
| private RSS, idle cell | **0.26 KiB** | — |
| private RSS, cell after running | **12.3 KiB** | < 1 MiB |

Idle cells cost essentially nothing because CoW pages are not faulted in until
touched — the "warm mote parked at near-zero cost" claim, observed.

## What is NOT proven (and what it would take)

1. **The VFS↔memslot join (ADR-0005) — the remaining gating risk.** These tests
   seal pages and execute from them directly, because the guest is kernel-less.
   A real mote kernel must make a guest `mmap(PROT_EXEC)` of `/tools/python`
   land on the sealed memslot rather than a page-cache copy. If it silently
   copies, the pages are sealed but nothing executes from them, and C1's
   guarantee evaporates in practice even though every test here still passes.
   **This is still the single highest-risk open item.**

   *Update, same day:* the vehicle for attempting it now exists (ADR-0004). A
   stock Fedora bzImage boots on the substrate in ~2.6 s to real userspace, a
   freestanding guest init runs and reports back over the console, and a sealed
   tool region is present in that kernel's physical address space above the
   e820 map — verified untouched across a full boot
   (`sealed_tool_survives_a_real_kernel_boot`). What is still missing is the
   **guest-side consumer**: a DAX-style direct mapping or a small driver that
   turns the sealed GPA range into something a guest `mmap` resolves to, plus
   the test that a guest write through that mapping still bounces. Until that
   exists, the join is unproven — the kernel booting is a prerequisite, not the
   result.
2. **Scale ceilings are untested beyond the numbers above.** 1,000 cells and 500
   sharers were the plan's gates, not the machine's limit.
3. **The tool bytes here are synthetic**, not a real CPython image. The sharing
   mechanism is size-independent, but a real image will exercise relocation and
   alignment behaviour these stubs do not.
4. **Guest-side attacks are limited to the memory path.** DMA, virtio devices
   and interrupt-path attacks do not exist yet because those surfaces do not
   exist yet.

## Verdict

C1 holds. No fallback to hash-verify-on-exec is needed: the ring-0 guarantee is
real, and per-tool sealing is not constrained by the memslot budget. Proceed —
with the VFS join treated as the next gating risk, not an implementation detail.
